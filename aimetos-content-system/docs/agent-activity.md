# Agent activity

The internal dashboard exposes a normalized operational timeline independently of n8n's own execution retention.

## Local endpoints

- `GET /api/agent-activity`: summary, important events and recent activity.
- `POST /api/agent-events`: ingest one normalized event. Reusing an event `id` is idempotent.

In mock mode, events are stored in `data/fixtures/agent-events.json`. The production target is the `AgentEvent` PostgreSQL model introduced by migration `0002_agent_events`.

## Event contract

Required fields are `agentId`, `agentName`, `workflowId`, `workflowName`, `executionId`, `correlationId`, `status`, `severity`, `title`, `summary`, `occurredAt`, `retryCount`, `requiresAttention` and `metadata`.

Statuses: `started`, `succeeded`, `failed`, `warning`, `waiting`.

Severities: `info`, `important`, `critical`.

Use a stable event ID generated by the source workflow. Retries must reuse that ID when they represent the same event. Never include credentials, raw customer payloads or sensitive prompt content in `summary` or `metadata`.

## n8n rollout

Each agent workflow should send events at meaningful boundaries: start, success, controlled warning, wait for approval and terminal failure. The HTTP endpoint must be protected before public deployment; the local mock endpoint intentionally has no production authentication yet.
